# Brain map

A generated knowledge graph of the kit, so an agent can go from a request to the right flow, screen, components, tokens, motion and tests **without reading the repo**. Everything in this folder except this README is generated by `scripts/brain/build.mjs` from the code (registry, imports, nav calls, CSS, journeys, visual refs). Never edit the cards by hand; run `npm run brain:build`. `npm run skill:check` fails when they are stale or when the graph has an `error` finding.

**The code wins.** The map is an index over the code, not a second spec. It never states what a screen should look like: that stays in the specs (`.claude/skills/<skill>/spec.md`), the briefs (`../flows/`) and the mapping docs (`src/flows/<flow>/MAPPING.md`, `FIGMA-MAPPING.md`). The cards link to those by line range.

## Layers and files

| Level | File | Size | Read it when |
|---|---|---|---|
| L0 | `INDEX.md` | ~1k tokens | always first: product areas, every flow with entry route, URL, skill, card |
| L1 | `flows/<flow>.md` | 0.5–9k tokens | you know the flow: screens, module, components, tokens, motion, nav in / out, tests, doc line ranges |
| L1 | `components.md` · `tokens.md` · `motion.md` · `journeys.md` | 2–4k tokens each | a design-system or navigation question that crosses flows |
| L2 | the spec / brief / mapping **line ranges** a card or `brain context` names | 100–500 tokens each | you need intended behaviour, copy, acceptance |
| L3 | source files: the screen module, then only the components you change | per file | implementing |
| — | `findings.md` | ~6k tokens | maintenance: broken links, cross-flow imports, undefined tokens, untested screens |
| — | graph.json (gitignored, built on demand) | ~2 MB | never read it; query it with `npm run brain -- …` |

Load the lowest level that answers the question. A card is enough to plan a change; source files are for the lines you edit.

## Stable IDs

| Entity | ID | Example |
|---|---|---|
| Flow | `flow:<id>` | `flow:cart` |
| Screen | `scr:<flow>/<screen>` (the route) | `scr:pdp/detail` |
| Component | `cmp:<Name>` shared · `cmp:<flow>/<Name>` flow-local | `cmp:ProductCard`, `cmp:cart/GroupProgressBar` |
| Token | `tok:<css var>` · group `tokgrp:<group>` | `tok:--nk-color-text-primary`, `tokgrp:button` |
| Motion | `mo:transition/<name>` · `mo:preset/<group>.<key>` · `mo:recipe/<Name>` · `mo:reduced-motion` · `mo:haptics` | `mo:recipe/Stagger` |
| Icon / asset | `icon:<origin name>` · `asset:<path>` | `asset:src/assets/cart/` |
| State / data | `store:demo` · `store:membership` · `store:<flow>` · `data:<export of src/data>` | `data:productById` |
| Test | `test:journey/<name>` · `test:visual/<name>` · `test:routes` | `test:journey/cart-checkout` |

IDs come from routes, component names and CSS variable names, so they only change when the code renames the thing itself.

## Relationships the graph records

`flow → screen → module file → files it imports` (named imports resolved through barrels to the defining file) `→ components · tokens · icons · assets · motion · stores · data`, plus `screen → nav → screen` (literal `nav.*('…')` calls; `~` = resolved through a const, helper or ternary), route strings in data (data-driven links), `test → screens` (journeys and visual refs) and `doc section → screens` (spec / brief / mapping headings that mention the route). For example (`npm run brain -- deps home/home`): `scr:home/home → HomeScreen.tsx → ProductCarousel → ProductCard → Price, ProductImage, WishlistHeart, QuantityStepper → type / color tokens → push pdp/detail → test:journey/cart-add-from-card`.

## Retrieval workflow (new screen, flow or change)

| Step | Do | Command / file |
|---|---|---|
| 1. Intent | Say in one line what the user wants to change and what they will do on it | — |
| 2. Product area | Find the flow and its journey position | `npm run brain -- context "<request>"` §1, `INDEX.md` |
| 3. Closest screens and patterns | Open the flow card; for a new page, also the card of the closest existing flow | `flows/<flow>.md`, `brain context` §2 |
| 4. Load only what's needed | The L2 line ranges and the screen module from `brain context` §3; `deps <screen>` for the component chain | `npm run brain -- deps <flow/screen>` |
| 5. Reuse vs gaps | Reuse what §4 lists (and `node scripts/design-context.mjs <words>`); §7 lists the request words nothing in the kit matches | `brain context` §4, §7 |
| 6. Research | Only for the gaps: Mobbin per `../../skills/noon-ui/references/research.md` (say so if it isn't connected) | — |
| 7. Ambiguities | Ask only what blocks the build: which flow, which reference wins (`truth`), what the user does | the screen's truth / verified in the card |
| 8. Implement | noon-ui workflow steps 4–8, tokens and components only | `../../skills/noon-ui/SKILL.md` |
| 9. Validate | The tests `brain context` §6 names, then `impact` for everything you changed | see Validation below |

## Impact workflow (before and after changing shared code)

1. `npm run brain -- impact <entity>`: `cmp:Price`, `--nk-color-text-primary`, `mo:transition/sheet`, `store:demo`, `data:productById`, `scr:cart/cart` or a file path. It lists the files that use it, every screen and flow those reach, the journeys and visual refs to re-run, the snap commands, and the docs that mention it (update them in the same change).
2. Change the code. Run the listed tests and snaps, read the PNGs.
3. `npm run brain:build`, then `npm run skill:check`.

`npm run brain -- path <from> <to>` gives the shortest navigation path between two screens (e.g. `home/home checkout/confirmation`), which is the order a journey test or a manual check should follow.

## Source of truth and provenance

- **Truth** (which reference wins: `bappzaar` / `figma` / `mixed` / `reference`) and **verified** (last side-by-side check) come straight from each `ScreenDef`. The cards print `*` when truth is only inferred from `source`, and `never` when a screen has no `verified` date. Never treat a reference-backed screen as verified unless it has a date.
- **Provenance labels** (reference-backed / kit-backed / inferred) are in `../inventory.md`; the map links to it instead of repeating it.
- A relationship exists in the map only when the code shows it. Dynamic navigation the generator can't follow is listed as `nav-dynamic` in `findings.md` rather than guessed.

## Validation rules

| Rule | Proven by | Covers |
|---|---|---|
| Behaviour and state transitions | `npm run test:journeys` (journeys per screen: `journeys.md`) | navigation, cart / wishlist state, filters, sheets, checkout, noon One, orders, empty / error states |
| Every screen renders without console errors | `npm run check:routes` (`test:routes`) | every registered screen |
| Visual fidelity against approved references | `npm run visual:ref` (`visual/refs/manifest.json`; a kit screenshot is never a reference) | the screens with a `test:visual/*` |
| Visual review of a flow | `node .claude/skills/noon-ui/scripts/snap.mjs <flow>`, read every PNG against the spec | any flow |
| Tokens only, no second design system | `npm run lint:tokens`, the design-guard hook, `findings.md` → `foreign-ui`, `undefined-token` | all of `src/` |
| Component reuse | `npm run check:duplicates`, `findings.md` → `promotion-candidate`, `cross-flow-component` | flows |
| Accessibility | journey checkpoint scans (`../tooling.md`), inert covered layers, sheets as dialogs | the journeys |
| Docs match the code | `npm run skill:check` (paths, tokens, routes, counts, this map is current) | skills and resources |
| Acceptance per flow | the "Acceptance" section of the flow's `spec.md` (line range via the card) | flows with a spec |

## Maintenance

- `npm run resources:build` rebuilds `../screens.md`, `../inventory.md` **and** this map; `npm run brain:build` rebuilds the map only.
- Adding a flow, screen, component, token, transition or journey needs no edit here: rebuild and commit the cards.
- `npm run brain:eval` measures retrieval against representative tasks and real commits (`eval-report.md`).
